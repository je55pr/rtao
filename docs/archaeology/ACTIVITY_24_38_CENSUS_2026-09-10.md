# PAL activity 24-38 census - 2026-09-10

## Scope and evidence boundary

This note catalogues activity IDs 24 through 38 from the European PAL `SLES_513.56` executable. The retained machine-readable evidence is generated by `tools/activities/activity_24_38_probe.py`; it contains derived metadata only and no executable or game-asset payload.

The strongest boundary is negative: **do not extend ordinary-race semantics past activity 23**. The result/progression path at `0x00238D50..0x00238DE8` executes its licence/result scan only when the current activity ID is `< 24` (`sltiu` at `0x00238D54`). Reused callback addresses and race-like activity names therefore do not make IDs 24-38 ordinary races.

## Descriptor and callback ownership

The launcher at `0x002106B8` selects descriptors 0-34 from `0x002BFE48` and 35-38 from `0x002C0090`. For every descriptor, bytes 0-3 are copied/consumed by the launcher, `+4` is a 24-byte settings pointer, `+8` is handler A, and `+12` is handler B.

For this special-activity range, byte 0 is safest described as the **raw setup/scene selector**. `0x00210704` copies it into the launch state and the subsequent branch chain chooses setup work from it. The ordinary-race proof that values 0-14 select `COURSE/C00.BIN` through `COURSE/C14.BIN` is deliberately not generalized here. Bytes 1-3 and the settings words likewise remain raw unless a special-activity consumer is separately traced.

Handler ownership is firmer. `0x00210730` reads descriptor `+12` and passes it to installer `0x0021DCD8`, so handler B is a descriptor-installed car/input callback slot. `0x00210D80` reads descriptor `+8` and passes it to task allocator `0x00204F88`; that allocator stores the pointer at task `+0x0C`, which the task runner later invokes. Handler A is therefore the scheduled activity callback.

IDs 24-34 and 38 reuse handler A `0x0022F3F8` and handler B `0x00252BA0`. IDs 35-37 replace handler A with dedicated state machines while retaining handler B `0x00252BA0`: Ski Jumping `0x0025BB00`, Fishing `0x002628E8`, and Beach Flag `0x00263040`. All three dedicated handler-A initializers allocate private activity state and schedule the shared framework callback `0x00236F88`. This establishes callback ownership, not shared gameplay rules.

## Selection gates

The 12-entry selector table at `0x002C0078` contains only two entries from this range: area index 8 selects ID 25 only, and area index 9 selects ID 24 only. IDs 26-38 are absent from that table, so their launch/availability gates are owned elsewhere. The numeric selector area indices are preserved without inventing location names.

Activity 24 also has a separately traced mode-8 launch path at `0x00210AD0..0x00210C3C`. Its opponent-construction loop at `0x00210BA0` is the already-documented Roulette/special path and must not be reused as an ordinary-race roster algorithm.

### Fixed-interior host gates and stamp effects

A second payload-free pass correlates the activity names with the retained PAL-derived fixed-interior census. These are **owner/registration host gates**, not proofs that the listed `SHOP/` package is the gameplay scene package. Post-text action `0x03` is traced at `0x0023D0A0`; its operand becomes a host-action parameter, so values such as 44 or 53 are preserved as host parameters and are not relabelled as activity IDs. ## Scene/package dependencies and known effects

Only one payload dependency in this range is currently closed strongly enough to name: the existing Roulette archaeology traces its physical wheel/car action to `ACTION/A19.BIN`, with update `0x002637E8`, wager host `0x00264318`, debit callback `0x00264604`, result matcher `0x00265048`, and payout callback `0x00264AD0`. Those facts remain a separate physical-action boundary; descriptor byte 0 (`0x11`) is not relabelled as `A19`.

For IDs 25-38, this census does **not** claim a concrete `COURSE/` or `ACTION/` filename. Some raw byte-0 values overlap ordinary course IDs, and several activities have race-like names, but neither fact proves package ownership. Dedicated handlers for Ski Jumping, Fishing and Beach Flag prove distinct activity state machines, not their asset package names.

Likewise, IDs 24-38 skip the ordinary licence/result-class block guarded by `<24`. No ordinary best-finish, top-six licence promotion, lap count, prize class, entrant count or opponent-settings interpretation is assigned to them. Roulette's separately traced wager/payout path is the only economic/progression effect reused here. Per-activity completion flags, unlock conditions and rewards for IDs 25-38 remain open evidence questions.

## Reproduction and retained evidence

Run from the repository root:

```text
python tools/activities/activity_24_38_probe.py C:\path\to\SLES_513.56 --json docs/evidence/activities/activity-24-38-census.json
python tools/activities/activity_registration_gate_probe.py docs/evidence/activities/activity-24-38-census.json docs/archaeology/SHOP_INTERIOR_DEPENDENCY_CENSUS_2026-09-01.json --json docs/evidence/activities/activity-registration-gates.json
```

The executable probe verifies five dispatch instructions before emitting output: descriptor split `0x002106B8`, handler-B read `0x00210730`, mode-8 branch constant `0x00210AD0`, handler-A read `0x00210D80`, and ordinary-progression bound `0x00238D54`. The executable JSON records the input executable SHA-256 plus names, raw descriptor bytes, raw settings words, callbacks and selector ranges. The registration-gate JSON records hashes of both derived inputs and emits only fixed-interior metadata, host parameters and stamp IDs. Both can therefore be regenerated without retaining copyrighted executable or game-asset bytes.
